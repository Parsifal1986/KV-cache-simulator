# 事件驱动离线模拟器（des_sim.py）— 2026-09-26 第一轮验证

09-21 用户提出的“时间线 + 事件触发”模拟器（计划见 results/cloud_20260921/MLDEV_WEEK_SUMMARY.md 末尾）。本轮完成计划的四项：步日志解析与代价回归、事件驱动主循环、decode 分配/逐出/retract、四个验证点对齐（本轮做了云端 c46 s36 与 c42 s0 两个点）。

## 工具（results/scripts/）

| 脚本 | 作用 |

| `des_sim.py` | 事件驱动模拟器。时钟只在步结束/到达时跳；每步规则逐条照抄 scheduler.py（见文件头 docstring） |

## 对齐真实调度器的要点（每一条都改变了结果）

1. **PrefillAdder 预算是实时属性**：锁住已匹配前缀会把它移出 evictable，`add_one_req` 在加锁后复查。旧写法把 available+evictable 算一次，c42 过度准入 → 203 次分配失败、124 次 retract、在飞超池；修正后 retract 0（GPU 全程 0 次 retract，一致）。
2. **准入预留**：新请求预留 min(max_new,4096)，运行中请求预留 new_token_ratio×剩余输出（0.7 → 0.098，600 步衰减，空闲复位）。
3. **overlap 调度器滞后一步**：batch j+1 在 batch j−1 完成时组好，所以请求只有在“上一步开始前”到达才进得了下一步（服务器空闲时无滞后）。不建模时小请求 TTFT 分布太窄。
4. **CUDA graph 悬崖**：cuda_graph_max_bs=32，bs>32 走 eager，decode 步 15–20 ms → 45–55 ms。c42/c46 开局 42–46 个对话，running 恰好在 29–39 之间来回，开局漂移全来自这里。
5. **逐出量**：SGLang 在 available<需求 时逐出“整个需求量”，不是差额。
6. **decode 代价回归量要用日志的 #token（在飞 KV，共享前缀只计一次）**，不是运行请求上下文之和。
7. **步代价要按 pod/臂各自拟合**：同一模型，两台云 pod 的 decode 斜率差 0.021–0.028 vs 0.042–0.047 ms/Ktok（±10–15%）。用混合拟合时，c42 的请求时刻漂移到墙前已 +45 s。

绝对值：模拟 LRU+D miss 3.65% vs GPU 3.11%。多出的未命中全部来自工具间隔 ≥30 s 后回来的对话（30–100 s +179K、>100 s +238K token）；间隔 <30 s 的请求与 GPU 逐 token 一致。逐窗 in-flight p50、running 数、decode 步长与 GPU 吻合。

TTFT 尾部：这个 pod 两臂并行跑，压力段（23–30 min）两臂都有 2–4 s 的单个 8192 chunk 步（正常 0.25–0.45 s）；c42 pod 与本地 lpm 从未出现。09-23 卡顿规则只剔掉 48 个请求（压力段里卡顿本身造成排队，规则不剔），所以这对的 GPU TTFT p99 不能当真值。模拟的 −26% 落在本地 fcfs/lpm 实测 −11%～−31% 之间。

## 目前能用来做什么

- 有压力但不撞墙的点：Δmiss、U p90 税、TM99、n>16k 可信（sd 很小，与 GPU 差 ≤5 个百分点量级）；U p99 会高估 RR 的收益；绝对 miss 偏高约 0.5pp。
- 墙点：只看撞墙时刻和方向，幅度不可信。
- 每个点一臂 90 s（单核），8 个重复 + 两臂约 3 分钟 → 可以替代 GPU 做选点扫描，但选定点仍需 GPU 标定。

## 第二轮定位（2026-09-26 晚）：误差链条与三处修正

按顺序排除/确认：
1. **墙里步代价没错**：用 GPU 步行按模型代价记账，墙窗口每分钟 53–63 s，纯 chunk 步实测/模型 1.02–1.07。旧版 decode_overlap 0.5 是在补它自己的代价误差。
2. **墙深来自排队丢前缀**：c42 LRU+D 墙窗多出的 3.0M 未命中全在模拟排队 >1 s 的请求上（整段历史丢失 194 vs 54）；GPU 墙里占用 0.93–0.95、队列均值 0.7–1.8，模拟顶到 0.99、队列 3.5–6.9。
3. **开环对照**（`des_sim.py --arrivals-from GPU_ARM`，每轮按 GPU 实测到达注入）：c42 LRU+D 7.31/GPU 7.21，RR-C+D 9.33/9.51，逐窗口吻合（30–35 min 28.2/29.5，35–40 min 9.25/9.00），sTTFT p99 4.53/4.55 s。→ 调度、缓存、步代价机制都对，误差全在闭环时序。
4. evict CPU（0.1 ms/次）、band 时钟用到达时刻、decode √K 形状：都不是原因。

三处修正（都已进 des_sim.py / fit_step_costs.py）：
- **decode 步长由最长序列决定**：step ≈ 8 + 0.01·K_inflight + 0.15·bs + 0.35·maxctx(K) ms。四条运行（两 pod）残差 MAD 1.0–2.6 → 0.23–0.44 ms，“第 20–30 分钟慢 4 ms”完全消失；系数跨 pod 一致。fit_step_costs.py --joint 从请求日志重建每个 decode 区间的最大上下文，和全部 decode 区间 + chunk 链联合拟合（参数 params_v2/）。
- **回放客户端每轮 +0.1 s**（`--turn-overhead 0.10`）：GPU 实测“本轮到达 − 上一轮完成”比录制间隔中位多 0.099 s，与间隔长短无关。
- **GPU 客户端中途丢对话**（`--drops-from GPU_ARM`）：09-20/21 这批运行里，旧版客户端遇到连接断开直接丢弃整段对话。c42 LRU+D 丢 4 条（含 boolq_performance#1，t135 起 92 轮×50–70K 上下文，约 1/10 个池），RR-C+D 丢 1 条；c46 两臂 4/2 条。

## 第三轮（2026-09-27）：一台机器一套参数 + 噪声带

原则（用户 09-27）：硬件只抽象成上层速率，同机固定（CPU 负载/内存带宽/GPU 型号吸收进常数），只建模随负载变化的部分（在飞 KV、批大小、最长上下文、prefill 量、KV 容量与策略）；每台机器 profile 一次；只用同机、CPU 负载平稳的运行，剔除冷启动与故障；目标是模拟落在同机噪声范围内。

- 机器档案 `machines/pod0920.json`：09-20 云 pod（4×H100，load ~11）12 条臂合并拟合的步代价 + 客户端每轮开销 + 噪声 + 首包延迟。各臂在合并参数下的步行系统偏差 −3.0%～+1.5%（spider2 −3%、banking −1～−2%、mldev ~0），一套参数成立。
- 噪声模型（同一批日志测得）：decode 速度因子每 1.3 s 重抽 σ 5.3%（1–30 s 自相关仅 +0.05～0.07）+ 60 s 慢漂移 σ 1.2%；prefill 步 iid σ 21%；客户端每轮开销中位 0.10 s、σ 0.46。
- 首包延迟：小请求 TTFT 与模拟之差随分位数增大且与负载无关 → 固定下限归零、每请求加对数正态延迟（中位 36 ms，σ 0.7）。TTFT 主体误差 20–70 ms → 2–11 ms。
- bk80 剔除：开环（GPU 到达时刻）仍 6.4% vs GPU 20.3%，步行残差却正常 → 不是速率问题；加上该点 LRU 本地/云端不一致、旧模拟需缩池 100–150K，不作为标定/验证数据（待查）。
- 结果（`des_run_pod0920_ensemble.sh`，10 臂 × 8 噪声种子，`des_noise_band.py`）：sp40/md34/md38 逐出侧全部落在噪声内；md42 Δ 全对但两臂绝对值偏悲观 ~1.5pp；sp48 单臂在带内，Δ 符号反（GPU RR −1.8pp，模拟 +3.3±1.8pp）。剩余系统偏差 = 撞墙点 RR-C+D 在模拟里更抖。
- 噪声带的上限问题：模拟由步耗时散布推出的噪声是下界。本地同配置重复（load 108–130）实测：mldev c46 RR-C+D miss +0.17pp / U p99 +20% / n>16k +6；banking c40 LRU miss −1.0pp / n>16k −11（该对 load 差 18，TTFT 差 13–32%）。pod0920 本身没有重复运行，真实噪声下界缺直接测量——下次上云时同配置重复 2–3 次即可补齐。

## banking 为什么对不上：trace 里的重复对话 + GPU 回放的 stitching（2026-09-27）

- banking_x3.pkl 的 666 个对话全部属于"内容逐 token 相同"的组：99 组 ×6、3 组 ×24，同组成员副本后缀相同、uuid 不同——基础 trace 是 34 个独立对话各重复 6 次（"34 任务×6"加压构造，agent 与用户模拟器都确定性，6 次运行完全一致）。x3 复制层有区分标记（#0/#1/#2 在首轮 prompt 内部分叉），这 6 份拷贝之间没有。mldev/spider2 跨对话可共享量为 0。
- GPU 回放默认 stitching：下一轮 prompt 用服务器自己生成的输出替换录制输出，拷贝之间只在首轮 prompt + 首轮输出前几十个 token 内共享（GPU 命中停在 t0len+82 这类位置）。旧模拟直接用录制 token，拷贝之间整段共享 → banking 模拟 miss 6% vs GPU 20%；同在飞量下 GPU 丢等用户对话的概率是模拟的 2 倍；等效容量差 ~150K。日志驱动重建（用 GPU 自己的时间线）能复现 22.6% vs 19.0%，缓存语义本身没问题。
- 修正：des_sim.py 默认模拟 stitching（`stitch_like_replay`：每个对话输出换成独有 token，下一轮按客户端同样的 k=LCP 规则拼接；`--no-stitch` 恢复录制原文）。bk80 两臂差值对上（Δmiss −7.3 vs −6.7pp、ΔU p90 −39 vs −45%、Δn>16k −528 vs −547、ΔTTFT p90/p99 −55/−43 vs −43/−48%），绝对值偏悲观 4–9pp（完全独有输出高估了分叉；GPU 重新生成常与录制前缀一致数十至上百 token）。其他负载不受影响。
- 建议：以后构造重复对话的 trace 时，像 x3 那样在首轮 prompt 末尾给每份拷贝插区分标记，让录制 token 本身就是"不同对话"，stitching 开不开结果都一致。

## 第四轮（2026-09-27）：GPU 实际 token + 两个新 profile 因子

- `--ids-from GPU_ARM`：每个 (对话, 轮次) 用该 GPU 臂实际发送的（已 stitching）prompt 和实际生成的输出；中途被客户端丢弃的对话（按录制的下一段间隔判断：本该在运行结束前发出却没发）在同一轮截断，运行结束时仍在等待的对话按 stitching 规则继续跑。时序仍来自录制间隔。bk80 由此对上（重复对话在 GPU 上保留的部分共享由真实数据自带）。
- 新因子 1：**客户端每轮开销随长度变化** = 30 ms + 2.84 ms/1K prompt + 5.8 ms/1K 上一轮输出（×lognormal σ 0.36）；原固定 0.1 s 对长上下文偏快。
- 新因子 2：**服务端入口开销** = 1.3 ms/1K prompt（request_received → 调度器等待队列，请求晚到调度器）；剩余首包延迟与长度无关（lognormal 中位 8 ms、σ 1.3）。修正前小请求 TTFT 差值随 prompt 长度从 −26 ms 升到 +49 ms，修正后 40K 以内各箱 ±11 ms。
- 已排查的小因子：evict CPU（0.1 ms/次）；比较窗口内的主机停顿（中段 ≤2%，随 pod 热身消失；运行末尾的"长步"是请求稀疏时的空闲，不是停顿）。
- 机器档案 machines/pod0920.json v2。结果（8 种子，GPU token，cross-pair Δ）：bk80 两臂与 Δ 全部 ±1σ；sp48 ±1.6σ；sp40 TTFT p80/p90 对上；md38 逐出 ±2.5σ、TTFT p90 偏快 15 ms；md42 Δ 对上、两臂绝对值偏悲观约 1pp，墙前逐窗口吻合，差异全在墙内（30–40 min）——反馈放大区，真实 seed 波动 ~2.65pp，暂不调。md34（运行停在 60%）LRU+D 臂不纳入。
- 剩余：mldev 40K+ 长 prompt 小请求 TTFT 仍偏快 +13～+56 ms；pod0920 无同配置重复 → 真实噪声带未测。
- 资源：模拟每进程 1 线程；`--ids-from` 单进程 10–18 GB → 并发 6（用户上限 ≤30 线程、≤100 GB）。

## 第五轮（09-27）：md42 墙内反馈放大区的精确定位

工具（scratchpad/des）：wall_pair.py（逐窗口配对 miss/TTFT）、drift_decomp.py（到达漂移 = 服务误差 + 客户端间隔误差）、dec_ratio.py、bin20.py、busy.py（忙时闭合）、gain.py；des_sim.py 新增 `--open-until T`（T 之前按 GPU 到达时刻开环，之后闭环）；fit_step_costs.py 新增 `--prefix-term`（试验，未采用）。

1. **墙内机制是对的**：开环（GPU 实测到达时刻）下墙内逐窗口对上——A 32–34 分钟 54.7±1.4 vs 56.2、34–36 分钟 42.0 vs 41.8；全程 miss A 7.26 vs 7.21、B 9.44 vs 9.51、Δ +2.2 vs +2.3pp。忙时闭合：墙内按模型累加 GPU 实际执行的步 = 30 秒窗口的 97–103%，步代价没有漏项。
2. **闭环多出的约 1pp 按切换时刻拆**（3 种子；closed = 全闭环，open = 全开环）：

   | 切换到闭环 | A (LRU+D) | B (RR-C+D) |
   |---|---|---|
   | 0（全闭环） | 8.21±0.34 | 10.51±0.23 |
   | 20 分钟 | 7.72±0.25 | 10.02±0.12 |
   | 30 分钟 | 7.47±0.09 | 9.87±0.04 |
   | 32 分钟（墙起点） | 7.27±0.26 | 9.97±0.05 |
   | 全开环 | 7.26±0.03 | 9.44±0.13 |
   | GPU | 7.21 | 9.51 |

   A：误差全部在墙前积累（从墙起点的真实状态出发闭环 = GPU）。B：约一半在墙前、一半（+0.5pp）在墙内产生。
3. **墙前来源**：客户端间隔误差≈0；每轮服务时间在 10–30 分钟偏短 0.1–0.35 秒，是 pooled 档案对 mldev decode 偏快约 1–4%（残差 md34/38/42 在 10–30 分钟普遍 +1–4%，spider −3%，banking≈0 → 一套参数跨负载的折中）。进墙平均漂移本身与墙深不相关（8 种子 r=−0.16/+0.25），起作用的是程序相位分布。
   - 剂量：只把 20–25 分钟减速 4% → A 8.21→7.80，B 不变；把 5–32 分钟整体减速 2% → **A 7.24±0.25（GPU 7.21）**，B 10.27±0.32（GPU 9.51）。
   - 试过的特征都消不掉这 ~1%：前缀线性 prefill 项（p_pre=0.53 ms/K，残差 +2.4→+2.3%）、c2/c1·bs/K/c1 等 decode 交互项（MAD 0.50→0.42 ms，20–25 分钟残差仍 +0.1–0.5 ms）。
4. **B 墙内来源**：从 32 分钟真实状态出发，模拟对墙内请求服务偏快（35–40 分钟每轮 −0.45 s，TTFT −0.33 s）→ 程序早回 → 压力大；开环下 B 墙尾（36–38 分钟）GPU 重算更多（miss 44.6 vs 35.5±4.2，TTFT p99 9.9 vs 5.1 s）。步代价已由忙时闭合排除，逐出 CPU 每分钟 0.01–0.03 s 也排除；差异在 RR-C 轮转在深队列下"谁丢 chunk"的路径，模拟自身在这个窗口的开环种子间波动就有 ±4pp。
5. **放大增益**：同一窗口开环种子间 σ 0.03–0.13pp，闭环 0.23–0.34pp（2–10×）；1–2% 的 decode 速率偏差 → 全程 miss +1pp（墙内窗口 +5～+12pp）。

**结论**：md42 剩余偏差 = pooled 档案对 mldev 约 2% 的 decode 速率偏差被墙放大（A 全部、B 一半）+ B 墙尾 RR-C 路径差异（接近模拟自身噪声）。不按负载改参数（违背一台机器一套参数）；根治靠整机微基准 profile 消除跨负载折中。撞墙点的验证应先跑开环/混合拆分再判定。

## 第六轮（09-27）：机器同一性核查 + 本机建档

**机器同一性**：GPU 日志 meta_info 的 `request_finished_ts − inference_time`（单调时钟起点）可作主机指纹。09-20 pod 的 12 臂全部 = 1774297239（同一台，两臂并行在 GPU 0,1 / 2,3）；09-21 pod（mldev c44/c46 s36）= 1774222353，**是另一台主机**。本机指纹每隔数天随容器会话变化，但都是同一台 8×H100 共享机。→ md42 的 ~2% mldev decode 偏差不是换机造成的。

**新工具 `results/scripts/profile_machine.py`**（一台机器建一次档）：
- `fit MANIFEST --out X.json`：步代价（fit_joint）+ 噪声（只用纯 decode 区间：1.2 s 尺度 σ、60 s 漂移 σ；prefill 链 σ）+ 客户端每轮开销（GPU 间隔 − 录制间隔，L1 回归 prompt/上一轮输出）+ 入口（dispatch − received，L1）+ 主机负载效应（运行内逐区间回归）+ 机器信息（开机指纹、GPU 对、负载）。
- `ttft MANIFEST --profile X.json --sim-dir DIR --suffix _n1`：用阶段 A 档案的开环模拟，从不排队的小请求 TTFT 残差定剩余入口斜率 + 首包延迟（中位数带负载拐点，σ 对齐 GPU p50/p80/p90）。
- `load` / `client`：只重测对应部分。
- 在 pod0920 上复现：步代价相同；客户端 19.6 ms + 3.0/K + 7.6/K输出（原 30 + 2.84 + 5.8），σ 0.32；纯 decode 噪声 2.6% + 漂移 2.4%（原 5.3% + 1.2% 混入了 prefill 方差）。

**des_sim 新参数**：`--load-from ARM`（该次运行的主机负载时间线）、`load_k/load_ref`（decode 随负载减速）、`ftd_load/ftd_knee`（首包延迟负载拐点）、`ovh_load/ingress_load/cpu_load_ref`、`ovh_run_sd`（每次运行固定的客户端开销偏移）、`ingress_base`。

**本机档案 `machines/local8xh100.json`**（35 臂，09-18..23，manifest `local8xh100_arms.tsv`）：
- 与 pod0920 对比：decode 慢 ~10–15%（d0 9.4/8.4，d_req 0.18/0.10），eager（bs>32）固定项 83 vs 40 ms，prefill 固定项 67 vs 34 ms（每 K 4.2 vs 9.1），8K 块约慢 15%；客户端更快（6.6 + 2.0/K + 3.5/K输出 ms）；首包延迟 12.9 ms + 0.55 ms/负载（>60）。
- **新因子：主机 CPU 负载**（共享机 9–480，中位 ~80；pod 恒 ~11）。运行内回归：decode 每 +100 负载慢 2.2%（分箱局部 ~4%/100），prefill 链几乎不受影响（+0.6%/100）；首包延迟在负载 >60 后陡升（<40：17 ms，100–120：57 ms，>120：62–73 ms）；客户端开销与瞬时负载无关（−0.002 ms/单位），但各次运行有 ±5 ms 的固定偏移（ovh_run_sd 4.7 ms）。跨运行偏差与负载相关 r=0.46（同配置内：ml46 RR-C+D 三次 +1.8/+0.2/+1.8% 对应负载 117/63/108）。
- **本机同配置真实噪声带**（ml46s36 RR-C+D × 3 次 GPU）：miss 2.67/2.53/2.84（sd 0.16pp），U p99 sd 10%，TTFT p50–p90 sd 15–16%（负载 63 的那次快 25%），p99 sd 10%。
